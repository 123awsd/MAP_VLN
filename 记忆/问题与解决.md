# 问题与解决

## GPU 在沙箱中不可见

- 现象：沙箱执行 `nvidia-smi` 无法连接驱动，但 PCI 设备可见。
- 用户确认：宿主机侧 `nvidia-smi` 正常。
- 当前判断：沙箱未映射 NVIDIA 设备，而非宿主机驱动损坏。
- 处理：不修改驱动；后续在实际 Conda/容器运行时重新验证。

### 结果

- 沙箱外 Habitat EGL 成功识别 RTX 5060 Ti 和驱动 580.126.09。
- 结论：宿主机驱动正常，确认为沙箱设备隔离。

## Habitat-Sim 0.3.3 与 Python 3.12 冲突

- 现象：Conda 的 0.3.3 Bullet 构建只提供 Python 3.9 变体。
- 处理：项目专属 Habitat 环境固定 Python 3.9.23；不影响其他环境。

## Boxer OWLv2 首次下载损坏

- 现象：早期受限网络产生部分文件，直接续传导致 zip 尾部不可读。
- 处理：只删除已确认损坏的 OWLv2 文件，从 0 字节重新下载。
- 验证：三个权重均能由 PyTorch 成功加载并已记录 SHA-256。

## Habitat-Lab 安装后的 Pillow 冲突

- 现象：Conda求解安装 Pillow 11.3.0，但 Habitat-Sim 0.3.3 要求 10.4.0。
- 处理：在项目专属环境固定 Pillow 10.4.0；Habitat/Habitat-Sim 导入成功。

## Docker Hub 基础镜像下载极慢

- 现象：CUDA基础镜像105MB层下载速度最终降到约20KB/s。
- 处理：安全中断，避免长时间无收益占用；没有遗留运行容器。
- 后续：优先配置项目级可选镜像源，或在FALCON正式Docker构建时复用已存在层继续拉取。

## 2026-08-23 桌面会话被 OOM 终止

- 现象：桌面/系统会话崩溃，但机器未重启；磁盘仍有约 179 GB，不是存储耗尽。
- 内核证据：8 GB swap 几乎耗尽后触发 OOM，杀死一个约 5 GB RSS 的 Chromium Python 进程。
- 共同诱因：当时另一个项目已有约 14 GB 的大型 Python 进程，本项目 OccuSG 编译又无并发上限地生成约 30 个 `cc1plus`，新增超过 10 GB 内存压力。
- 责任判断：本项目无上限编译是直接触发因素之一，不能归咎于沙箱或磁盘。
- 修复：`colcon --parallel-workers 1`、CMake/Make `-j2`，并增加 12 GiB 内存/2 GiB swap 预检。
- 复验：安全构建时只有 2 个 `cc1plus`，最低仍有约 22 GiB 可用内存，swap 未继续消耗，构建成功。

## RViz 容器无法连接 X11

- 现象：首次启动显示 `Authorization required` 和 `could not connect to display :1`。
- 原因：`/home/uav/.Xauthority` 是空文件，当前 GDM cookie 实际位于 `/run/user/1000/gdm/Xauthority`，且容器 hostname 不匹配原 cookie family。
- 处理：提取当前 display cookie，转换为 FamilyWild，保存到 Git 忽略的 `runtime/rviz.Xauthority` 并只读挂载到容器。
- 结果：RViz 1.14.26 正常启动；容器未映射 NVIDIA GUI 驱动，因此使用 llvmpipe OpenGL 3.1，显示功能正常但渲染性能低于原生 GPU。
- 录制和回放脚本会自动刷新 cookie，桌面重启后也无需手工运行 `xhost`。

## 相机倒着走、Box 不明显与点云遮挡

- 原因：Habitat 位置跟随与 FALCON 独立 yaw 轨迹可能不同向；且 optical 姿态曾直接用作 body odometry。
- 修复：默认面向实际移动方向，optical pose 仅用于深度建图，body pose 用于 odometry/path。
- 验证：最终 bag 中 97 个移动采样的前向对齐度平均值和最小值均为 1.0000。
- Box 只有 2 个是上游高置信融合阈值的真实结果，不是 RViz 丢消息；可视化改用 26 个去重候选的高亮线框，正式 2 个结果仍保留。
- occupied cloud 降为 1 px/alpha 0.22，depth cloud 和 candidate viewpoints 默认关闭。

## RGB 卡顿、Box 一次性出现且与房间错位

- 原因：旧 bag 只有 5 Hz RGB，同时包含大量高频规划 Marker；Box 来自另一次 episode 且融合 CSV 的时间全为 0。
- 修复：RGB 提升到 10 Hz，移除 `pos_cmd`、`position_cmd_vis`、`viewpoints` 录制；同次探索同时保存 Boxer 关键帧，按 `first_seen_ns` 回写 bag。
- 验证：RGB 实测 9.95 Hz，总消息 5,326；31 个 box 按 18 个事件渐进出现。
- 同回合对齐验证：Box 中心到 occupied map 最近距离中位数 0.036 m、最大 0.060 m，无超过 1 m 的房间外框。

## 大房间缺失、通道被当作房间

- 根因：Stage 2 场景图的物体来自完整 497 帧回合，但 OccuSG 房间多边形误用了早期 40 帧 `hm3d_stage1` 格栅，导致未知区域 62.3% 并漏掉右上大房间。
- 解决：用 `hm3d_stage1_complete_v3` 的 497 帧 RGB-D 重建格栅，未知比例降至 37.3%；按 `area<=2.0 m² && adjacency_degree>=2` 将连接型空间标记为 `corridor`，保留导航拓扑但不参与卧室/客厅目标匹配。

## 床把同一房间切成 R2/R3、区域数大于真实房间数

- 直接从占据图删除所有家具会把房间覆盖从约 40 m² 降到约 8 m²；虽然数字碰巧变成 7，实际丢失了约 80% 的有效房间，因此未采用。
- 采用保守的床 OBB 定向合并：只有同一个大床同时接触至少两个非通道区域时才合并，本图仅合并原 R2/R3。
- 对小于 1 m² 的孤立碎片先判定父房间，再规范化并入父房间；加入楼梯屏蔽后最终规划层为 6 个主要房间、4 个通道、0 个碎片。2 个源碎片只保留在 `geometric_regions` 中用于追溯，不再进入 RViz、规划或 Qwen 清单。

## 楼梯被压平成房间

- 根因：旧占据建图对所有高度的 RGB-D 端点都执行 XY 投影，向下楼梯和下层射线因此在当前层刻出一个 5.60m² 斜形伪房间。
- 证据：HM3D 语义 ID 445 为 `stairs railing`、ID 462 为 `stairs`；楼梯点最低比当前层低约 2.7m，与旧伪房间空间重合。
- 修复：只融合 0.15–1.8m 单层高度带；楼梯/栏杆合并成一个带 0.20m 净距的禁行区；排除楼梯旁小型无物体孤岛。
- 结果：自由栅格从 30,887 降为 26,095，楼梯禁行 3,296 格；房间从表面 7 个修正为 6 个，楼梯不进入规划、Qwen 或 RViz 房间层。
- 房型推断对床、厕所、灶台等强线索加权，避免“有床也有电视”时被电视误判为客厅；没有充分物体证据时仍诚实显示 UNKNOWN。

## 第二阶段目标扎堆与 Box 相互遮挡

- 目标实例分配先处理候选稀缺类别，再优先选择不同主要房间并最大化间距；选定目标后，访问顺序仍由 A* 联合规划求几何最优。
- 不可达的房间偏好会显式退回同类别可达实例，并把真实使用的 object ID 写入 candidates，避免元数据与执行目标不一致。
- 静态融合物体用细蓝框常驻；任务相关物体叠加统一粗洋红框，状态差异只写在文字与五角星结果中，不再用多种 Box 颜色干扰点云。

## 条件分支无法表达“多个位置任选其一”

- 当前 `conditional_rules` 适合表达“A 失败后固定激活 B”，但不能准确表达“目标可能在 A 或 B，由路线决定先查哪里，找到一个就停止”。
- 设计保留为 AND–OR 任务图：顺序依赖是 AND/precedence；同一语义目标的多个位置是假设 OR group，采用 `first_success` 完成策略。规划状态记录已完成语义目标和已失败位置假设，每次观测后剪枝并重规划。

## 大模型给出的位置稳定性不是天然校准概率

- “桌子位置通常可信、桌面杯子位置不太可信”是有价值的常识，但大模型单次生成的 0.87 不能当成真实校准概率。
- 课题范围收缩为类别/关系级三档先验：`high`（结构/大件家具）、`medium`（可移动家具/灯具）、`low`（杯盘/遥控器等随手物品），避免伪精确数值。
- 用户所需的增信单位是独立任务回合，而不是同一回合的帧数或多视角。VLM 给出初始 `stability_prior_tier`；长期记忆保存 `confirmed_same_missions`、`confirmed_changed_missions`、`unobserved_missions` 和当前 `location_persistence_tier`，任务结束后更新一次。
- 同一档位必须可追溯来源：规划记录同时输出 `semantic_prior_tier`、可空的 `experience_tier`、最终 `effective_tier` 与 `tier_source`。规划只使用 effective，先验只负责冷启动/证据不足时回退，经验档达到最低独立任务证据后才覆盖先验，避免重复计权。
- `unobserved` 不能当作 moved：只有目标区域被充分覆盖且检测可靠时，not_found 才算 `confirmed_changed`；遮挡或未覆盖不改变档位。杯子连续多个独立任务都在同一桌面位置时可以提高该“位置槽位”的持久性，但不声称辨认出了同一个外观相同杯子实例。
- 单次任务期间环境保持静态，不进行运动目标跟踪；跨任务持久性只服务下一次任务的 AND–OR 位置假设排序。

## RGB 话题不断流但中段画面冻结

- 现象：轨迹 Marker 周期刷新时，第一视角会连续数秒保持同一画面，容易误判为回头路时 RGB 丢失。
- 证据：旧包 399 帧中有 159 对内容完全相同；冻结区间 odometry 位移为 0，最长 4.3 秒，说明是规划等待而非 ROS 时间戳缺口。
- 修复：FALCON 静止超过 0.5 秒后，Habitat 相机以 25°/s 原地扫描；移动恢复时立即面向真实位移方向。主 3D 默认关闭容易误导的规划轨迹，2D 窗口单独展示轨迹和 frontier。
- 验证：新包 400 帧、10.0 Hz，最长相同画面仅 0.2 秒；地图更新持续到末帧前 0.007 秒；10 倍速回放完成后 RGB 最后一帧与两个 RViz 窗口均保留。

## 主动扫描新回合出现房间外离群框

- 证据：27 个调试融合框中，chair 与 shelf 中心距末帧 occupied cloud 分别为 2.123 m 和 1.092 m；截图中的孤立紫框是真离群检测。
- 修复：`inject_progressive_boxes.py` 默认以 0.75 m 做最终地图距离门控，仅过滤 bag 中的可视化 Marker，不删除 Boxer 原始/融合 CSV。
- 验证：最终 bag 显示 25 个框、19 个渐进事件，RGB/地图/轨迹消息保持不变。

## 3D 点云地面/天花板遮挡与轨迹语义混淆

- 原因：RViz 的 PointCloud2 显示不能直接做几何过滤；固定世界 Z 上限无法处理斜顶，且顶棚点云本身有厚度。`/planning/travel_traj` 还是累计命令历史，而非当前规划或 Habitat 实测路径。
- 修复：派生节点根据 odometry 推断地面；对每个 0.10 m XY 柱求局部最高 Z，并剥离其下 0.60 m 顶棚层，使过滤面随斜顶变化。绿色 Path 使用 Habitat pose，琥珀色 Marker 由当前 B-spline 实时采样，红色命令历史改为可选层。
- 验证：默认 bag 末帧 46,696 点中剔除 11,052 个地板点、15,476 个局部顶棚点，保留 20,168 个墙体/主要障碍点；被识别顶面覆盖 Z=1.55–3.75 m，证明不是固定水平截断。

## 旧包被误称为完整探索、UAV 在两个 Frontier 间振荡

- 原因一：旧录制入口固定运行 40 秒，`scan_complete` 只是文件名；末帧仍有 8,056 个 active Frontier 点。
- 原因二：Habitat 执行器使用地面 navmesh `try_step`，FALCON 却按 UAV 自由空间规划；遇到栏杆、楼梯或挑空时，规划位置为 `(-0.59, 2.16)`，实际位置卡在 `(0.90, 2.00)`，导致反复重规划。
- 修复：`file_bridge_node.py` 监听 FALCON FSM 的 `/planning/replan=2` 并写完成标志；录制入口等待该标志，超时拒绝生成 complete 包。UAV 模式精确跟踪 PositionCommand，navmesh 仅作为显式可选地面模式。
- 验证：新回合 248.303 秒后日志显示 `No frontier detected` 并进入 `FINISH`；末帧 active Frontier=0、occupied map=234,056 点，覆盖率约 506.7。

## Matterport 单值凭据无法下载 minival

- 现象：用户提供了一个 Matterport API 值，但当前 Habitat 数据下载流程要求 token ID 与 token secret 两个字段；无认证、Bearer 和把单值用于 Basic 的尝试均未通过。
- 处理：不记录或猜测第二个秘密，也不反复请求导致锁定；改用本机已安装的三个官方 HM3D example 做几何多图回归。
- 边界：开发场景 `00861` 有真实 Boxer/semantic 在线验证；另两图仅用 synthetic semantic anchors，报告中明确标注。
- 后续：获得完整 token ID/secret 后下载 minival，并逐图重跑第一阶段生成真实 scene graph。

## VLM 把参照目标和验证目标混为一谈

- 现象：“counter 上有没有 cup”一类指令需要靠近 counter，但最终应验证 cup；早期 schema 只有一个 target。
- 修复：增加 `verification_label`，保留 `target.label` 作为导航锚点；加入 `on` 关系并升级 prompt/cache 版本。
- 防护：缓存结果读取时也做规范化；所有非条件任务初始 active，precedence 只控制 ready 状态。

## 条件分支难以稳定覆盖

- 现象：开发场景里电视确实可见，正常阈值会走 found 分支，无法在每次回归中覆盖 cabinet 激活。
- 处理：演示入口仅对 `observe_living_room_tv` 使用 10,000 pixel 受控阈值，其他任务保持真实阈值。
- 结果：电视 7,696 pixels 被判为该测试条件下 not_found，cabinet 随后激活并以 101,126 pixels 验证 found；报告明确这属于分支测试而非检测失败。

## 多种子评测生成了无解观察任务

- 现象：首轮论文矩阵只有 192 条成功记录、13 个失败项；`00337` seed 23 的所有目标都挤在约 0.2 m 范围内，空间任务也常缺候选。
- 原因一：用随机 navigable point 的高度生成 topdown map，可能落到 4.13 m 的小楼层/平台，而不是主楼层。
- 原因二：仅按 free cell 或固定侵蚀净空放置 synthetic anchor，没有直接验证目标观察环是否存在 free + LOS pose。
- 修复：采样多个 navmesh 高度并选择最大连通面积楼层；逐 cell 检查最小观察环的 24 个角度，只从至少一个候选可行的池中做 seeded farthest sampling；空间任务的 box yaw 与已验证方向对齐。
- 结果：3 scenes × 3 seeds × 5 cases × 6 methods 共 270/270 完成，failures=0。

## 观察质量消融与完整方法路线相同

- 现象：初版 `terminal_weight=0.35` 时，`joint_astar` 与 `no_terminal_quality` 平均路径和 viewpoint quality 基本相同，说明观察项在几十米路径尺度下太弱。
- 处理：将代价写成有明确组成的 `L + 0.25T + 2.0C_view`，其中时间同时考虑水平、升降与 yaw；增加消融验收，要求完整方法 viewpoint quality 严格高于去掉观察项。
- 结果：路径优势基本保持，观察质量从 0.889 提高到 0.937；平均路径从 42.63 m 增至 42.97 m。该结果明确呈现路径—观察质量 trade-off，后续仍需学习型或真实可见面积 utility。

## 00150 残留 Frontier 后停止探索

- 根因不是 frontier 数据未发布，而是 FSM 把“当前视点因碰撞无法执行”误当成全局完成。另外还存在已到访端点反复被选中、A* 连续无路两类停滞。
- 修复后不再立即结束：同一碰撞或规划失败视点连续 3 次失败时，只剔除该视点并刷新 frontier 池；同一已执行端点到访 3 次后才退役；只有可达 frontier 视点真正耗尽才正常 `FINISH`。碰撞恢复仍无替代目标时用独立 `collision_stall` 状态，不会伪装成完成。
- `min_candidate_occupied_clearance: 0.3` 表示候选视点与最近 occupied voxel 至少相距 0.3 m，不是对 occupied voxel 本身做 0.3 m 膨胀。本 Habitat 点机器人配置同步使用 `bspline_opt.safe_distance: 0.3`，候选环为 0.5–2.0 m。
- 00150 `tuned_v7` 在 213.77 s 后以 `/planning/replan=2` 正常完成，无 `collision_stall`。最后一个 A* 不可达视点经 3 次失败被退役，随后确认可达视点已耗尽。
- RViz/bag 中的 `frontier_pcl` 可以仍有点：它包含 frontier 几何可视化或 dormant/历史数据，不等于 frontier 仍有可达候选视点。终止判定应联合 FSM 状态、`/planning/replan` 和日志中的 active frontier 候选集。

### 00150 左上角增强探索验证（2026-08-28）

### 多楼层 frontier 探索顺序（2026-08-29）

- 现象：二维 HGrid 会同时收到不同高度的 frontier 顶视点，规划器可能在同一轮交错选择不同楼层；当前楼层仍有待探索区域时就跨层，容易留下未消除的 frontier。
- 修复：FALCON 增加可配置的 floor-priority 模式。`getTopViewpointsInfo()` 只把当前楼层高度带内的候选交给 HGrid；当前层候选耗尽后，才切换到最近的更高楼层。HGrid 仍保持 `map_dimension: 2`，不增加三维连通图的规划开销。
- 参数：`floor_priority_enabled: true`、`floor_priority_band: 0.85 m`、`floor_priority_min_separation: 1.2 m`。活动楼层以初始里程计高度作为 Floor 1，后续楼层按实际 frontier 高度动态发现，不写死楼层数。
- 兜底：若地图更新延迟导致低楼层 frontier 在高层阶段才出现，会回退到最高的低楼层候选，而不是直接把探索判为完成；日志会记录开始楼层、楼层切换和延迟回访。
