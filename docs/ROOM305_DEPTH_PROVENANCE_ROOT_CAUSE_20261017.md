# 305凸出：深度来源闭环

本次完成原始bag深度—采集位姿—同时间戳RGB—官方加修复场景第一交点核查，不改变旧分割。

## 直接证据

诊断范围原X(-6,-4.5)、Y(4.05,4.45)、Z(5.5,8.3)，仅用于溯源不进入算法。扫描实际深度得到8个包含该范围端点的采集帧。保存逐帧depth、mask、端点、RGB和红色标注。RGB显示标注集中在卫生间斜顶左侧狭缝及其后方，不是地面。

从8帧按像素顺序等间隔抽查860条射线，以原采集位置发射，加载原始HM3D及同一14个修复物体，核对第一交点：824条命中修复对象，36条命中原场景。修复对象实际ID9=third_west（西侧封闭墙），ID10=third_ceiling（顶面封闭板）。819/860条第一交点距离与记录深度差小于3cm；其余41条存在较早交点，不能忽略渲染/碰撞网格边缘差异。以上是该诊断ROI选中像素样本，不是全部305体积的归因比例。

run的simulator_command.json明确加载同一repair.json。load_scene_repair使用同一OBJ同时设置render_asset_handle和collision_asset_handle，因此修复物体既参与碰撞，也进入传感器图像。

## 根因定位

该凸出相关深度大量来自人工包围场景的封闭面，不是原始建筑房间表面。局部斜顶边缘存在能透视后方修复物体的通道，深度记录远端修复面，射线积分形成FREE；二维房间算法把连通且有FREE的区域纳入305。人工修复几何的观测语义与真实建筑结构混用，是本例已证明的上游问题。

尚不能仅由这些证据判定狭缝在真实建筑中是破损扫描还是设计开口，也不能给全部突出体素打上伪造标签。三维FREE连通不等于真实房间延伸。

## 公共修复对象

优先区分场景修复物体的用途：仅防出界的碰撞壳与有依据重建的传感器表面不能混用。需要在场景加载/传感器有效性层处理，不按305坐标过滤最终房间。若碰撞壳改为仅碰撞，需要验证不进入RGB/深度且碰撞仍生效；未知/穿出原网格的射线不能作为无限FREE清空。既有700秒数据已经含这些观测，不能删除表面点就声称消除了其射线清空历史。

本次未修改冻结运行、repair文件或在线传感器。GPU驱动不可用，无法完成新的深度渲染回归；CPU碰撞第一交点核查已完成。不能将仅改配置的未验证版本替换基线。后续完整公共修复必须同时验证碰撞、深度有效性、积分和三层分割，而不是继续贴末端形状补丁。
